# 04 · 四条失败路径与证据

> 所有结论均来自**在真机上的实测**（含 2026-08-09 与 2026-08-10 两轮）。

## 共同的根结论

Pico 4 的 2D 悬浮窗触摸 **由 XRShell 原生 `create_device()` 创建的 `virtual_input_device` 承载**，并通过**原生流程内的"路由注册"动作**投递到当前聚焦的 2D 窗口（NS_APP 虚拟 display）。

除了那条原生流程，**没有其它入口**能让触摸进入 2D。

---

## 路径 1 · 标准 Android 注入

**尝试**：`adb shell input tap`、`input -d <disp> tap`、`sendevent` 写各 /dev/input 节点。

**结果**：2D 窗口无任何反应。

**原因**：2D app 在独立虚拟 display（NS_APP），不在主屏 input 路由；且 `virtual_input_device` 只被 XRShell 原生流程驱动，外部 `sendevent` 写的 ABS 坐标事件不被系统当作 2D 触摸处理。

**证据**：两次实测，Via 前端无日志、无动作。

---

## 路径 2 · 自建 MT 多点 uinput 设备

**尝试**：写 C 程序（`code/mtinject`）自建 `ABS_MT_SLOT max=9` 的多点 uinput 设备，包括设备名也叫 `virtual_input_device`、bus/vendor/product 与原设备一致。

**结果**：
- 设备被系统识别为 **MT 触摸屏**（`Classes` 含 MT、`Session mode multi-touch`）。
- 但 **viewport 被路由到主屏 display0（4320x2160）**，**不路由到 2D/NS_APP**。
- `Last Cooked Touch: pointerCount=2` —— MT 注入协议本身有效，但触摸落在主屏，到不了 Via。

**结论**：系统**只把 XRShell 进程创建的 `virtual_input_device` 当作 2D 触摸设备**；外部自建设备（哪怕同名同属性）不会进入 2D 的路由。

---

## 路径 3 · Xposed hook 替换 XRShell 设备（最深入）

**尝试**：用 LSPosed 模块 hook XRShell 的 `UInput.nativeCreateDevice()`，把它返回的设备替换成我们自己创建的 MT 多点设备（`ABS_MT_SLOT`），并 hook `nativeSendMotionEvent` 转成 MT 注入。

在调试过程中**成功修复了两个深层问题**（这些经验本身很有价值）：

| 问题 | 根因 | 解决 |
|---|---|---|
| 设备被当成"外部设备" `isExternal=true` | uinput 的 **bus 用了蓝牙/其它**，而原设备是 `BUS_VIRTUAL(0x0006)` | 用 `BUS_VIRTUAL` |
| `Sources=0x1103` ≠ 原设备 `0x1703` | **KEY 集合不完整**（缺 D-pad/媒体等键） | 补全原设备全部 25 个键 |

**修复后设备已与原设备完全一致**：
```
IsExternal: false
Sources:    0x00001703      ← 与原设备一致
DeviceType: touchScreen, mode-direct, multi-touch
Slot:       min=0 max=9     ← MT 多指
name:       virtual_input_device
bus:        0006 / 1234 / 5678
```

**但即便如此：viewport 仍固定在主屏 display0，不跟随 Via（2D）。**

**铁证（控制实验）**：连"纯复刻原单点设备（bus 已修、isExternal 已对、无 ABS_MT）"通过 hook 创建，viewport 也是主屏。而**不 hook 时**（XRShell 原逻辑）原设备 viewport 会动态跟随当前 2D app。

**结论**：**"路由到 2D 窗口"是 XRShell 原生 `create_device()` 流程内部的主动动作**（可能在 `create_device` 之后由 XRShell 后续逻辑把设备绑定到 NS_APP display）。用 hook（无论在 Java 层替换 `nativeCreateDevice` 还是改设备属性）都会**绕过这条原生路由**，导致触摸固定在主屏。

---

## 路径 4 · idc 路由 `pvr-virtual-input` 到 2D

**尝试**：用 Magisk overlay 修改 `/system/usr/idc/pvr-virtual-input-0.idc`，加入：
```
touch.displayId = virtual:com.picovr.systemext,1000,NS_APP[mark.via],0
```
把 pvr-virtual-input-0（系统内 MT 多点设备）关联到 Via 的 NS_APP display。

**结果**：
- idc overlay **生效**：`AssociatedDisplay` 确实变成了 `displayId='virtual:...NS_APP[mark.via],0'`。
- 但 **Touch Input Mapper 是 `mode-disabled`**（viewport displayId=-1, SurfaceWidth=-1），`sendevent` 注入 MT 双指后 Via **无任何反应**。

**结论**：`pvr-virtual-input-*` 本质是 Pico 内部（vrshell/socialhome/主屏）专用设备，触摸 mapper 平时 disabled；即便 idc 把它关联到 2D，触摸也不投递。

---

## 汇总表

| # | 方案 | 核心结果 | 卡点 |
|---|---|---|---|
| 1 | 标准 input / sendevent | 2D 无反应 | 2D 在独立 display，不在主屏路由 |
| 2 | 自建 MT uinput 设备 | 识别为 MT，投主屏 | 系统只路由 XRShell 创建设备到 2D |
| 3 | Xposed 替换 XRShell 设备 | 属性全修对但仍主屏 | 路由在原生流程内，hook 绕过 |
| 4 | idc 路由 pvr-virtual-input | 关联生效但触摸不投 | 设备 Touch Mapper disabled |
